# FairTransmog reverse-engineering findings

## Evidence policy and current gate

Every reverse-engineering claim is marked **observed**, **inferred**, or **unknown**. Observations from recovered transcripts remain historical until explicitly revalidated; stale absolute addresses are not a runtime profile. A disk hash match establishes executable identity, not the validity of a runtime adapter.

- **Observed, source and host build, 2026-10-16:** the recovered project originally referenced a missing `src/game/appearance.cpp`. The logging-only replacement builds with MSVC x64 in both Release and diagnostic presets. All five CTests pass in each preset: memory, profile, disposable-host bootstrap, armor inspector, and deployment fixtures. The inspector runs 15 tests with the current asset fixture enabled; deployment fixtures run eight groups, including copy-corruption rejection. Reports are `re/observations/ctest-release.xml` and `re/observations/ctest-diagnostic.xml`; tested source and DLL hashes are in `re/observations/host-verification.json`. The bootstrap test checks the completed fail-closed log in a separate host process; this is not an installed-game loader or appearance test.
- **Observed, source:** the logging-only bootstrap has no game callbacks, hooks, appearance operations, inventory operations, menu operations, or diagnostic apply controls. Matching and unknown executable identities both end with those features disabled.
- **Unknown:** individual-piece application, five-piece application, native visual refresh, current-ownership eligibility, native-menu integration, serialization acceptance, and multiplayer behavior. No claim of transmog functionality or online safety follows from compilation.
- **Observed, live, 2026-10-18 (supersedes the bullet above for visual apply):** single-piece and five-piece visual-only apply/restore of ordinary armor (set 480, type 0, actor 530) over the TEST character's Samurai layered set worked by writing `player+0x13754+slot*4` and calling native `sub_142041700(player,1,0)` on the busiest game thread. Saved IDs untouched. Details, the corrected `slot*0x26CC00` user chain, and the retraction of the 2026-10-17 prototype result are in `PROTOTYPE_MILESTONE.md`. Ownership, menu integration, persistence across loads, serialization, and multiplayer remain unknown.
- **Observed, live, 2026-10-18:** `tools/live/inspect_inventory.py` counts sets that have metadata part pointers (485 non-layered), which is catalog presence, not ownership.

- **Observed, same binary, `sub_140523680`/RVA `0x523680` and `sub_140523950`/RVA `0x523950`:** the factory requests `0x4CF0` bytes and reaches a constructor storing primary table VA `0x142FA77F8` at the object's first qword. - **Observed, same binary, `sub_140525370`/RVA `0x525370`:** the list builder visits `0x2F0` catalog indices, filters native type values 2/3, consults availability predicates, deduplicates IDs, and fills category-local arrays. These are catalog iteration bounds, not inventory ownership bounds.
