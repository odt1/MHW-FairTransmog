## Implementation sequence

### 1. Establish a recoverable, current-build runtime profile

- Locate the active Steam account’s complete `SAVEDATA1000` save and relevant metadata; make a timestamped, hash-verified backup with the game closed before any runtime writes. The save contains all slots, not just TEST. Do not change Steam Cloud settings or silently restore over later progress.
- Use the existing RE harness with Binary Ninja through `bnctl`, and user-mode Cheat Engine through `cectl`. Keep new analysis artifacts and trusted probe scripts in separate directories under the new project. No DBK/DBVM, new integrity bypass, or unrelated tool updates.
- Validate selected-slot readiness, local player identity, inventory iteration/count, and the canonical saved versus live appearance state. Use read-only observations of known vanilla layered changes to identify the correct fields and callbacks. Do not reuse the old editor’s scanner, slot stride, or Steam-DLL offset.
- Record binary identity, RVA/function, observations, inferences, and unknowns in `re/FINDINGS.md`. Resolve addresses from the actual module base and require unique signatures, expected instruction shapes, readable ranges, and valid object identities before enabling a feature.

### 2. Build the native diagnostic DLL

- Adapt the DLSS project’s CMake/static-CRT, logging, and narrow memory helpers into the separate project, retaining applicable BSD notices. Reuse `FindSection`, `FindPattern`, `RipTarget`, and `SafeRead` from `C:\Projects\MHW DLSS\src\memory.h/.cpp`, with checked protection changes and validated inputs rather than copying unchecked pointer writes.
- Keep `DllMain` minimal; bootstrap outside loader lock. Start logging-only and fail closed on unsupported builds, ambiguous signatures, invalid state, or incomplete profiles. Do not require an `Initialize` export: the checked loader source uses `LoadLibraryA` (`MHW-QuestLoader/MHWLoader/loaderdll.cpp:20–33`); verify actual installed-loader behavior with the smoke test.
- Run appearance operations on the verified game/UI thread, never an arbitrary worker. Prefer a menu-local callback; if the main update callback is needed, preserve the existing chain because DLSS already hooks `sMhMain` vtable `+0x30`. Avoid unsafe hot unloading; restart for DLL replacement/removal.
- Add development-only apply/restore commands, disabled by default and restricted to active slot 3 TEST. Snapshot the original appearance, preserve unchanged slots and pigments, and restore only while the same character/context remains valid. Compile arbitrary-ID controls out of the player-facing build.

### 3. Prove individual and set appearance application

- First apply and restore a known valid layered piece as a control; then a verified ordinary real-armor appearance; then a coherent five-piece ordinary set. Validate slot masks and ID domains before each operation.
- Establish the native refresh/apply path and distinguish preview state, committed appearance, and saved state. A raw saved-field write that requires an area change is useful evidence, but not completion of the native live-application milestone.
- Make no equipment-item, stat, material, currency, progression, or permanent unlock-bit writes. Stop and report a blocker if real IDs cannot be applied safely; do not substitute guessed model IDs or persist invented identifiers.

### 4. Add current-ownership eligibility

- Write a read-only armor catalog inspector using the verified schema, with provenance and explicit unresolved records; use `python -I` outside extracted directories. Do not build/run the editor or modify/repack `armor.am_dat` for this feature.
- Enumerate the selected character’s actual equipment through a validated native iterator/count or bounded structure. Confirm whether inventory IDs reference table rows or another domain. Keep inventory enums distinct from armor-table enums; exclude weapons, charms, and verified placeholders.
- Deduplicate copies, include equipped pieces, preserve slot/variant/gender distinctions, and treat indivisible full-body armor separately after its ownership representation is established.
- Preserve all legitimate vanilla layered options. Additional eligibility derives only from currently owned real gear in this character, not recipes or other save slots. Recheck on menu refresh, commit, and relevant loadout application; stale rows/loadouts must not bypass ownership. Do not maintain a permanent “ever owned” unlock list.

### 5. Integrate the native layered menu

- Trace `uGUIEquipOuter` construction, list generation, availability filtering, preview/cancel, confirmation, and loadout application on this build. The GlobalPendant example is a source-level equipment-menu extension reference, not a source of trusted current addresses.
- Add eligible ordinary armor through verified menu-local enumeration/filtering, preserving native names, icons, ordering, controls, and ordinary layered entries. Keep any temporary row storage alive until its menu is destroyed.
- Scope the behavior to layered selection/application, not forging or global ownership queries. Do not globally change armor types, forge requirements, or unlock bitsets. Preview/cancel must not commit selection.
- Use real, engine-accepted appearance IDs and normal serialization. Defer synthetic records or broader table changes unless direct-ID experiments prove them necessary and a separate safe design is established. Clearly report unsupported cases rather than silently skipping them or claiming full coverage.
